# Aiven 歷史修課 Migration 部署程序

此文件是部署準備，不授權執行正式 migration。執行前須另行確認目標、維護窗口與批准。

## 備份與前置檢查

1. 暫停所有會修改資料或結構的服務，確認沒有並行 DDL；核對資料庫名稱、版本、表、主鍵、唯一索引、外鍵、CHECK 和目前筆數。重新檢查而非依賴舊筆數。
2. 建立整庫一致性加密備份，保存在 Git 專案外的受限位置；備份含個資及密碼雜湊。先在獨立 MySQL 完整還原、核對每表筆數及資料指紋、主鍵、索引和外鍵。確認加密備份可用於災難復原。
3. 確認 `User_Course_History` 已是 004 結構，不重跑 004。記錄每一步的執行時間、操作者、執行前後結構及結果，日誌不包含個資或憑證。每步確認完成才進下一步；遇錯立即停止，不重跑整份 SQL。
4. 本次唯讀檢查顯示四個既有真實使用者中，兩筆缺少學號對應、四筆未設定密碼 Hash。須先設計並驗證不覆蓋既有 Profile 的安全帳號遷移；正式環境不可啟用明文 JSON 登入作為捷徑。

維護窗口由負責人先停用網站及背景工作中的寫入入口，等待進行中交易結束，再以唯讀查詢確認連線目標及基準；不以程式設定推測寫入已停止。將執行紀錄放在受限的 `Documents/CSP-Backups/<本次部署>/migration-execution-log.md`，不放進 Git。

### 加密整庫備份還原

本機整庫備份以 gzip + AES-256-GCM 串流加密，金鑰由目前 Windows 帳號的 DPAPI 保護；備份必須在同一 Windows 使用者設定檔下驗證或解封。若該設定檔遺失，可能無法復原，正式部署前另保留經驗證的獨立安全備份。此備份涵蓋 `defaultdb` 使用者表，不含 MySQL 伺服器層級帳號及權限。

在加密備份目錄執行 `node restore-full-backup.mjs --verify` 可只驗證認證與壓縮完整性。需要復原時，先建立全新 MySQL 8.4 容器，容器名稱使用 `csp-full-recovery-` 加 12 位小寫十六進位，設定獨立隨機 root 密碼並使用 `--network none`；待容器就緒後執行 `node restore-full-backup.mjs --container <容器名稱>`。工具拒絕非隔離或已有使用者資料庫的容器，先完整驗證備份，再串流解密還原，不寫出明文備份檔。還原後核對逐表筆數、結構、索引、外鍵與資料指紋；容器內 MySQL 資料本身並未因備份加密而自動加密，必須限制 Docker 與主機存取。

## 逐步執行與驗證

| 步驟 | 執行前 | 執行後與紀錄 |
|---|---|---|
| 011 | 確認歷史表存在且沒有 `source_credit_record`。 | 確認 `source_credit_record VARCHAR(255) NULL` 存在；核對筆數與既有資料。 |
| 012 | 確認 `Local_History_Attestations` 不存在，`User_Profiles.user_id` 主鍵及 InnoDB 可作外鍵。 | 確認表、索引與外鍵；此表及其本人聲明**僅供本機測試**，不得視為官方身分驗證。 |
| 013 | 確認 `course_id`、`source_payload` 與 `Unmatched_Course_History` 尚不存在；核對原欄位型別、字元集與 collation。 | 先確認 ALTER 結果，再確認待查表、唯一索引及外鍵。`requirement_type` 和 `graduation_category` 必須維持 `utf8mb4_unicode_ci`；放寬 NULL 後核對原資料。若第二個 DDL 失敗，第一個可能已提交。 |
| 014 | 確認 013 待查表完整，且 `source_identity` 與 `uq_unmatched_source` 不存在。 | 確認欄位、可空性及唯一索引。MySQL 唯一索引允許多筆 NULL，不能視為完整去重保證。 |
| 015 | 確認 012／013 完整，`source_payload` 存在；新欄位及索引不存在。預先統計符合回填條件的筆數，檢查 DDL／UPDATE 鎖定與執行窗口。 | 分別確認歷史表 ALTER、聲明表 ALTER 及 UPDATE。核對欄位、索引、資料與 `updated_at` 變化；如中途失敗，不可重跑整份檔案。 |

每一步以 `information_schema.COLUMNS`、`STATISTICS`、`KEY_COLUMN_USAGE` 和 `SHOW CREATE TABLE` 做只讀比對，並記錄 `COUNT(*)`；不得在日誌保存查詢出的個人資料。使用下列紀錄格式，013 與 015 各陳述式分開填寫：

```text
步驟／陳述式：
目標資料庫與操作者：
執行前檢查及備份驗證：
開始／結束時間：
結果：未執行／成功／失敗／狀態不明
執行後欄位、索引、外鍵與筆數核對：
錯誤碼及下一步核准狀態：
```

部署後以唯讀查詢核對 Profile、歷史紀錄、既有索引與外鍵及代表性 API，確認舊資料可讀、新增 NULL 不會被錯誤納入原有畢業／推薦計算。正式真人 MyFCU 同步入口在官方身分核對與安全驗收完成前保持停用。

## Windows 本機 MyFCU 同步

1. 先準備已安裝的 Google Chrome、專案依賴，以及團隊提供的本機 Aiven 連線和 CA 設定。更新分支後執行 `npm --prefix server install` 安裝擷取工具。
2. 停止目前佔用 `5173` 或 `27151` 的開發服務。在專案根目錄執行 `npm run dev:myfcu`，再開啟 [本機排課系統](http://localhost:5173/)。
3. 同學使用自己的排課系統帳號登入，從首頁選擇「同步 MyFCU 修課紀錄」。本人在開啟的 Chrome 視窗登入官方 MyFCU。回到預覽核對資料與匯入目標後，再確認匯入。
4. 有新增紀錄時，首頁會顯示匯入摘要並依新資料立即重排。若重排失敗，可用首頁「套用偏好排課」重試。新增 0 筆時保留目前課表。

這個指令使用 Windows 本機 SessionImport 模式，前端與後端只聽本機連線。由使用者本人確認校務資料與系統帳號歸屬，正式站同步仍須校務身分核對。

## 失敗處理與復原

1. 立即保持寫入停用，記錄錯誤碼及最後成功的陳述式；不要輸出 SQL 資料列、密碼或 token。
2. 唯讀盤點實際欄位、索引、外鍵和記錄筆數。MySQL DDL 會隱含提交；`ROLLBACK` 不會撤銷已成功的 DDL。
3. 依盤點與經核准的補救方案處理。不得盲目重跑、刪欄或直接覆蓋現存資料。必要時先在新隔離資料庫驗證從加密整庫備份還原，再於維護窗口依已批准的復原程序操作。
4. 復原後核對逐表資料、結構與 API，再恢復服務；如無法證明一致，維持寫入停用。
