## 1. 結論

1. **先做標籤空間的 User Embedding，協同過濾後做。** User Embedding 只用使用者自己的資料
   （歷史修課、互動事件、明確偏好），現在就能做；協同過濾需要很多真實使用者，現在沒有。
2. **每個模型各自產生一個 −1～1 的分數，各自加到課程原始分數上。** 排課紀錄分開保存每一項，
   看得出是哪個模型讓這門課加分或扣分。
3. **協同過濾在真實使用者不足時只能跑 shadow**（算分、記錄、不影響排序），這是 roadmap #6
   原本就寫明的條件。

## 2. 現況

### 2.1 現有的兩個探索功能

系統目前有兩個「探索」，用的訊號都不是使用者學到的興趣檔案：

| 功能 | 程式 | 用什麼找課 | 有沒有用到 rag_tag |
| --- | --- | --- | --- |
| 興趣探索卡片 | `interestExplorationService.js` | 使用者**填寫的**興趣與關鍵字，比對課程標籤（標籤完全相同 ×2、主分類相同 ×1、學程相同 ×1），再挑分類路徑不重複的 8 門 | 有，但只比對**填寫的**興趣，不讀 `Learned_Tag_Interests`，也不看歷史修課 |
| 系外與通識探索清單 | `explorationService.js` | 從一門**已修過的課**出發，用課程說明的字元二元組 TF-IDF 算餘弦相似度，每個系所／通識領域取一門 | 沒有，比對的是課程說明文字 |

所以兩者都不會「依照使用者學到的 rag_tag 興趣，推出相近的課」：

- 興趣探索卡片只看使用者當初填了什麼，之後收藏、加選、標記不感興趣都不會改變它推的課。
- 系外探索清單一次只從一門課出發，比對的是說明文字，不是 rag_tag，而且不影響排課。

### 2.2 現有的排課接點

| 位置 | 作用 |
| --- | --- |
| `scheduleService.js` `loadTagInterestContextSafely()` | 每次排課讀使用者標籤興趣檔案，替每個候選課算分 |
| `tagInterestRanking.js` `buildTagInterestContext()` | 產生 `coursesBySectionId[sectionId] = { score, evidenceTagCount, matchedTags, reason }` |
| `tagInterestRanking.js` `scoreCandidateWithTagInterest()` | 單課：`基礎分 × (1 + 0.6 × score)` |
| `tagInterestRanking.js` `scorePlanTagInterest()` | 方案：自由選擇課的平均分數，`方案偏好分 × (1 + 0.6 × 平均)` |
| `scheduler.js` 第 2956 行附近 | 必修群組與補修失敗群組不套用興趣分數 |
| 環境變數 `TAG_INTEREST_RANKING_MODE` | `off`／`shadow`／`active` |

注意 `基礎分 × (1 + 0.6 × s)` 等於 `基礎分 + 0.6 × 基礎分 × s`，也就是**在原始分數上加一項**。
第 5 節沿用這個寫法，讓每個模型各加一項。

### 2.3 標籤興趣檔案的限制

`scoreCourseTagInterest()` 只比對**完全相同的標籤**，而且只看使用者對每個標籤的分數平均，
不看「整體興趣輪廓有多像」。目錄有 6,769 個標準標籤，多數只出現在少數課程上，
很多課程因此落到 `no_user_signal`。**這個比例我還沒算**，列為階段 0。

### 2.4 資料量

- 帳號：10 位 Persona（D0009001～D0009010，人造）加上少數真實帳號。
- 互動事件：10/07 稽核時 510 筆，其中真實 `plan_chosen` 只有 4 筆。
- `User_Course_History`：各帳號都有歷史修課，Persona 的也是人造的。

## 3. User Embedding

### 3.1 核心想法

把課程和使用者放進同一個向量空間。課程向量由課程的 rag_tag 算出來；使用者向量是
他修過、互動過的課程向量的加權總和。兩個向量越接近，代表這門課越接近他的興趣。

### 3.2 課程向量的三種做法

| 做法 | 是什麼 | 要不要外部模型 | 本構想的定位 |
| --- | --- | --- | --- |
| **A. 標籤空間** | 每門課是 6,769 維的向量，每一維是一個標準標籤；課程有這個標籤就填值，值用 TF-IDF（越少見的標籤權重越高） | 不需要，純計算 | **一定要做，先做** |
| B. 文字 embedding | 用預先訓練好的語言模型，把一段文字轉成一串數字（例如 384 或 1,536 個），意思相近的文字數字也相近 | 需要，**決定用 API**（見 3.2.2） | **要做**，接在 A 之後；用來讓意思相近的標籤互相對得上 |
| C. 從互動資料學出來的向量 | 矩陣分解或雙塔神經網路（見 3.2.3） | 不需要外部模型，但需要大量真實互動 | 等真實資料足夠 |

#### 3.2.1 A：標籤空間

```text
課程 c 在標籤 t 的值 = 1（c 有 t） × idf(t)
idf(t) = log( 課程總數 / 有標籤 t 的課程數 )
```

- 用 `crossCourseMatchEligible=true` 的標籤，**加上 `too_common` 的常見主題**
  （機器學習、人工智慧、Python 等，2026-10-14 使用者決定以低權重納入，由 idf 自動壓低）。
  單課專屬標籤與 `explicit_generic` 排除。這是向量專用的規則，現有標籤興趣模型的規則不變。
  實作見 `server/src/skills/tagVectorSpace.js`（[階段 1 報告](./2026-10-14-tag-vector-stage1.md)）。
- 以課程代碼（`catalog_course_code`）為單位，不以班級為單位：同一門課不同班級內容相同，
  每學期班級代碼會換。
- idf 讓「程式設計」這種很多課都有的標籤影響小，「強化學習」這種少見的標籤影響大。

它解決的問題：標籤興趣檔案是「逐一比對標籤、取平均」，標籤空間是「比較整體輪廓」。
一個修過三門 AI 課的人，向量會集中在 AI 相關的標籤上；一門新課只要和這些課共用幾個少見標籤，
相似度就會高，即使它沒有任何一個標籤是使用者直接互動過的。

它沒解決的問題：兩個意思相近但文字不同的標籤（例如「機器學習」與「類神經網路」）
在 A 裡仍是兩個不相干的維度。這是 B 才能補的。

#### 3.2.2 B：文字 embedding 怎麼運作

1. 有人預先用大量文字訓練好一個神經網路，訓練目標是「意思相近的句子，輸出的數字串要相近」。
2. 使用時把一段文字丟進去（例如一個標籤名稱，或一門課的「課名＋標籤＋簡介」），
   得到固定長度的數字串（向量）。
3. 向量之間用餘弦相似度比較。模型從訓練資料學到「機器學習」和「類神經網路」常出現在相似的上下文，
   所以兩者的向量會接近。

**需要外部模型。** 有兩種取得方式：

| 方式 | 例子 | 優點 | 缺點 |
| --- | --- | --- | --- |
| 呼叫 API | OpenAI `text-embedding-3-small`（專案已有 OpenAI 金鑰） | 不用裝東西；品質好 | 每次計算要付費（量很小）；課程公開資訊會送到外部 |
| 本機執行 | 多語言小模型，在 Node 用 ONNX／transformers.js 執行 | 資料不出去、不付費 | 要下載數百 MB 的模型檔、增加相依套件；伺服器要有足夠記憶體 |

**決定：用 API。** 金鑰沿用伺服器的 `OPENAI_API_KEY`，不寫進程式或文件。

**階段 2 實測後的實際做法（2026-10-14，見[階段 2 報告](./2026-10-14-tag-embedding-stage2.md)）**：
模型改用 `text-embedding-3-large`（small 對短中文詞偏重字面）；**只送標籤名稱，不附分類路徑**
（附上後分類文字主導相似度）；門檻 τ = 0.70（large 的相似度整體較低）。下方「用途 1」表格中
「名稱加分類路徑」與「τ 起點 0.80」是原構想，已被取代。相近表存在
`server/src/data/tagVectorNeighbors.json`。

**B 的兩個用途**

| 用途 | 送進 API 的文字 | 用在哪裡 |
| --- | --- | --- |
| 1. 標籤相近表（主要） | 每個標準標籤的名稱，加上所屬主分類、子分類名稱（例如「類神經網路｜人工智慧｜機器學習」），讓同名不同義的標籤分得開 | 3.5 的 `s_vec`：讓意思相近但文字不同的標籤也能對上 |
| 2. 課程文字向量（次要） | 課名＋標準標籤名稱＋課程簡介 | 3.7 的「和你修過的〈○○○〉相近」清單；取代或對照 `explorationService.js` 現有的字元二元組 TF-IDF |

**為什麼用途 1 是主要的**：使用者向量依決定只用標籤（3.3）。用途 1 不改變向量所在的空間，
只是讓標籤之間有了「相近」關係，使用者向量、課程向量、推薦理由都還在標籤空間裡，
理由仍然說得出「你修過的課有『機器學習』，這門課的『類神經網路』與它相近」。

**標籤相近表怎麼算**

1. 6,769 個標籤各算一次向量，存起來。
2. 每個標籤找出餘弦相似度最高的前 5 個其他標籤，只保留相似度 ≥ τ 的（τ 起點 0.80，
   階段 1 人工抽查 50 組後定）。
3. 只對 `crossCourseMatchEligible=true` 的標籤建相近關係，與 A 的資格規則一致。
4. 結果存成「標籤 → 相近標籤與相似度」表，排課時直接讀，不呼叫 API。

**成本與頻率**

- 標籤名稱很短，6,769 個合計約數萬 token；課程文字視簡介長度約數十萬 token。
  以文字 embedding 的計價，一次全量計算的費用很低，但實際金額動工時依當下價格估算。
- 只在三種時候重算：標籤目錄改版、新學期課程匯入、換 embedding 模型。
  每筆存內容雜湊，內容沒變就不重送。
- 排課、探索、推薦理由**都不即時呼叫 API**。API 掛掉只影響重算，不影響使用者。
- 換 embedding 模型時，新舊向量不能混用，必須全量重算；每筆記錄模型名稱與版本。

**送出去的資料**：只有標籤名稱、分類名稱與課程公開資訊（課名、簡介），**不含任何使用者資料**，
也不含 `subject_id`。這一點寫進隱私說明。

#### 3.2.3 C：從互動資料學出來的向量

- **矩陣分解**：把「使用者 × 課程」的互動表，拆成「每個使用者一個向量」與「每門課一個向量」，
  讓兩者的內積接近真實的互動強度。學完之後，相似的課程向量會靠近，即使它們的標籤完全不同——
  例如資料顯示修「財務管理」的資工學生常接著修「金融科技」，模型就會學到兩者相近。
- **雙塔模型**：兩個神經網路，一個吃使用者特徵、一個吃課程特徵（可以包含 A 的標籤向量），
  各自輸出向量，訓練目標同樣是讓會互動的使用者和課程向量接近。這就是先前進度報告提到的
  「深度模型、端到端神經網路」。

兩者都是**從很多人的行為裡學**，本質上是協同過濾的一種，所以和協同過濾卡在同一個阻塞：
沒有足夠的真實互動，學出來的只是 Persona 設定。

### 3.3 使用者向量

```text
user_pos = Σ 權重 × 時間衰減 × course_vec(c)    （正向訊號的課）
user_neg = Σ 權重 × 時間衰減 × course_vec(c)    （負向訊號的課）
```

正負分開存，不相減：相減會讓「喜歡 AI、討厭會計」的人變成一個指向奇怪方向的向量。

**訊號來源與權重**：

| 來源 | 權重 | 說明 |
| --- | --- | --- |
| 歷史修課（選修、通識、系外，已通過） | +0.5 | **一定要算**；必修排除 |
| 歷史修課彈出視窗：勾「喜歡」 | +1 | 見 3.4 |
| 歷史修課彈出視窗：勾「不喜歡」 | −1 | 見 3.4 |
| 有興趣、收藏、高評分 | +1 | 沿用 `rag-tag-interest-v1` |
| 自願加選 | +0.5 | 沿用 |
| 瀏覽 | +0.1，單課上限 0.15 | 沿用 |
| 明確不感興趣、因內容退選 | −1 | 沿用 |

時間衰減沿用 120 天半衰期與舊學期 ×0.5。**歷史修課的時間衰減要另外訂**：
大一修的課到大四仍然代表興趣的一部分，用 120 天半衰期會讓它幾乎歸零。
建議歷史修課改用學期數衰減（每早一學期 ×0.8），實際數值在階段 2 看分佈後定。

**初始向量（冷啟動）**：只用標籤，不送進文字模型。

1. 使用者填寫的興趣與關鍵字，經現有的 `buildExplicitTagInterest()` 對應到標準標籤，
   對應到的標籤在向量裡填 `idf(t)`。
2. 只對應到主分類或子分類、沒對應到具體標籤的，不展開成底下所有標籤（與現有規則相同），
   只保留在分類興趣裡。
3. 對應不到任何標籤的關鍵字（`unmappedTopics`）不進向量；如實記錄，讓之後能看出有多少關鍵字對不上目錄。
4. 有事件或歷史修課之後，初始向量以固定先驗權重（概念同 `κ=2`）參與總和，資料越多影響越小。

**同意**：只在 `personalization_learning` 同意時計算；撤回即刪除。

### 3.4 歷史修課彈出視窗

目的：修過不等於喜歡。歷史修課預設給 +0.5 的弱訊號；讓使用者自己指出哪些是真的喜歡、
哪些其實不喜歡，把弱訊號換成強訊號。

**時機與位置（已定）**

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 位置 | 排課主頁（`/`，`DashboardPage`）上的對話框 | 使用者到這頁就是要排課，回答會立刻反映在這次排課結果上 |
| 新使用者第一次跳出 | 完成 `/onboarding` → `/setup` → `/interest-exploration` 後，第一次進到排課主頁、**按「產生課表」之前** | 興趣探索問的是「未來想修什麼」，這裡問的是「修過的覺得如何」，兩者接在一起問題一致；放在產生課表之前，第一次排課就用得上 |
| 既有使用者 | 功能上線後第一次進排課主頁時跳一次 | 他們已經走過引導流程，不會再經過興趣探索 |
| 新學期 | 歷史修課新增了上學期的成績後，只列**新增的那幾門**，再跳一次 | 不重問已經回答過的課 |
| 略過 | 「稍後再說」關閉對話框；同一批課**不再自動跳出** | 避免每次進頁面都被打擾；略過等於全部「普通」，仍以 +0.5 計入 |
| 之後修改 | `/setup`（個人設定）加一個「我修過的課」區塊，可隨時打開修改 | 讓使用者改變心意時有地方改 |
| 不跳出的情況 | 未同意 `personalization_learning`；沒有可列出的歷史課 | 未同意時回答無法用來學習，問了也不能用 |

**內容**

| 項目 | 決定 |
| --- | --- |
| 列出哪些課 | 已通過的選修、通識、系外選修；**排除必修**；排除沒有可比對標籤的課（它們對向量沒有貢獻） |
| 排列 | 依學期由近到遠分組，每組標學期 |
| 每門課的選項 | 喜歡／普通／不喜歡三個按鈕，預設「普通」 |
| 一次列太多時 | 超過 15 門時先顯示最近兩學期，其餘收合在「顯示更早的課」 |
| 按鈕 | 「儲存」與「稍後再說」；「儲存」只送出有改成「喜歡」或「不喜歡」的課 |
| 說明文字 | 一句話說明用途：「你的回答會用來推薦相近的選修與通識，必修不受影響。」 |

**資料**

| 項目 | 決定 |
| --- | --- |
| 寫到哪裡 | 新的互動事件類型（構想名稱 `history_course_feedback`），和其他事件一樣只存 `subject_id`、帶標籤快照、180 天到期 |
| 「已經問過」怎麼記 | 依該使用者已有的 `history_course_feedback` 事件與「略過」事件判斷，不另開欄位 |
| 會不會影響標籤興趣檔案 | 會。「喜歡」與「不喜歡」也是 rag-tag 興趣的明確證據，同時進入 `computeTagInterestProfile()` |
| 180 天到期的問題 | 事件到期後，那門課退回 +0.5 的預設值，不會變成反向。到期前在設定頁提示可重新確認 |

注意：新增事件類型要動 `interactionEventSchema.js`、API 與文件，屬於後續實作，本文件不處理。

### 3.5 課程分數

```text
s_vec = softcos(user_pos, course_vec) − λ × softcos(user_neg, course_vec)

softcos(u, c) = uᵀ S c / sqrt(uᵀ S u × cᵀ S c)
S = 單位矩陣 ＋ 標籤相近表（3.2.2，只有相似度 ≥ τ 的標籤對有值）
```

`S` 是 A 與 B 的接點：沒有 B 時 `S` 就是單位矩陣，`softcos` 退回一般餘弦（純 A）；
有 B 之後，意思相近的標籤也會互相貢獻相似度。這讓 A 可以先上線，B 做好再接上，
不需要改公式。`S` 很稀疏（每個標籤最多 5 個相近標籤），計算成本仍然很低。

~~再於候選池內標準化（減池內平均、除以標準差、壓到 −1～1）~~ —— **階段 3 實測後已改**
（[階段 3 報告](./2026-10-14-user-tag-vector-stage3.md)第 3 節）：標準化會讓六成以上的課只因為沒有共用標籤
就變成負分。現行做法：

```text
s_vec = min(1, 正向相似 ÷ 池內正向相似 P95) − λ × min(1, 負向相似 ÷ 池內負向相似 P95)
正向、負向相似都是 0 → s_vec = null（沒有證據，不加分也不扣分）
```

只有負向證據（明確不感興趣、因內容退選）會讓分數變負。實作見 `server/src/skills/userTagVector.js`。

### 3.6 推薦理由

向量本身不可解釋，但標籤空間的向量可以：相似度是每個標籤的貢獻加總，
可以直接列出貢獻最大的 2～3 個標籤，以及「你修過的〈○○○〉也有這些標籤」。
這些都是可查證的事實，符合現有 `explanationFaithfulness.js` 的要求。
接上 B 的標籤相近表後，理由可以多一種：「你修過的課有『機器學習』，這門課的『類神經網路』與它相近」，
相近關係本身是查表得到的，同樣可以查證。

### 3.7 探索功能怎麼用

| 用途 | 做法 |
| --- | --- |
| 興趣探索卡片 | 目前依填寫的興趣排序；改成依 `s_vec` 排序，讓收藏、加選、歷史修課都會改變推的課 |
| 「和你修過的課相近」清單 | 從使用者向量出發（不是只從一門課出發），列出當學期最相近的選修、通識、系外，標明共用哪些標籤；從單一課程出發的版本改用 B 的課程文字向量，與現有字元二元組 TF-IDF 做 A/B 對照 |
| 系外選修的保留名額 | 目前用 `matchesInterestKeyword()` 挑課，改用 `s_vec` 取前 N 門 |
| 多樣性 | 保留現有「分類路徑不重複」與「每個系所一門」的規則，避免全部推同一類 |

這幾項都不改排課的計分，可以和第 5 節分開做。

## 4. 協同過濾

### 4.1 互動表

- 列：使用者。用 `subject_id`，不用學號（見 4.2）。
- 欄：課程代碼。
- 值：沿用 3.3 的訊號與權重（含歷史修課與彈出視窗的回答）。
- **資料來源只有保留「哪位使用者對哪門課做了什麼」的紀錄**：

  | 來源 | 提供什麼 | 鍵 |
  | --- | --- | --- |
  | `Interaction_Events` | 收藏、加選、退選、評分、不感興趣、選擇方案等逐筆課程互動 | `subject_id` ＋ `catalog_course_code`／`section_id` |
  | `User_Course_History` | 已通過的選修、通識、系外選修 | 學號 ＋ 課程代碼；讀入當下換成 `subject_id`（4.2） |
  | 歷史課回饋事件（未來，3.4 的 `history_course_feedback`） | 使用者對修過的課標的喜歡／不喜歡 | 寫入 `Interaction_Events`，同上 |

- **`Learned_Tag_Interests` 不是互動表的來源。** 它是已經彙整成「標籤 → 分數」的興趣檔案，
  沒有保留使用者對哪門課做了什麼，無法用來算課程與課程的共現。它的用途是
  User Embedding 的初始與輔助訊號（第 3 節）和排課時的興趣檔案分數 `s_tag`（5.1）。
- **必修不進表。** 同系同年級的人必修全部相同，放進去只會學到「同班同學修一樣的課」。

### 4.2 為什麼用 `subject_id` 不用學號

`subject_id = "v1:" + HMAC-SHA-256(密鑰, 學號)`，是 #33 隱私規則定的假名。

1. **主要資料來源本來就沒有學號。** 互動表的課程互動主要來自 `Interaction_Events`
   （含未來的歷史課回饋事件），它依設計只存 `subject_id`。用學號反而要另外把學號接回去。
2. **外洩時認不出是誰。** 沒有密鑰，`subject_id` 無法反推學號。互動表記錄了誰修了什麼、
   對什麼有興趣，是敏感資料；用假名時，就算這張表外流，也無法對應到具體學生。
3. **協同過濾會把 A 的資料用在 B 身上。** 計算過程只需要「這兩個人行為像不像」，
   不需要知道他們是誰。不需要的身分資訊就不該進入計算。
4. **刪除與撤回一致。** 撤回同意或刪除帳號時，所有分析表都用同一個 `subject_id` 找到並刪除。

功能上沒有損失：使用者登入後，伺服器用同一把密鑰從學號算出他的 `subject_id`，
就能找到他自己的那一列。

歷史修課表 `User_Course_History` 目前以學號為鍵（它是服務資料，不是分析資料）。
組互動表時要在讀入當下換成 `subject_id`，學號不寫進互動表或任何協同過濾的輸出。

### 4.3 做法

**Item-item（先做）**：「選了 A 的人也常選 B」。

```text
sim(A, B) = 同時選 A 與 B 的人數 / sqrt(選 A 的人數 × 選 B 的人數)
            × 共同人數 / (共同人數 + β)          ← 支持度收縮
s_cf(u, c) = Σ sim(c, j) × u 對 j 的回饋強度      （j 取與 c 最相近的前 K 門）
```

只有 1 個人同時選兩門課時，原始相似度會是 1.0；收縮後才會接近 0。
離線每天算一次，存成「每門課最相近的前 K 門」。

**User-user**：「和你相似的人選了什麼」。用 3.3 的使用者向量定義誰和誰相似，
而不是用互動表本身；兩個人即使沒修過同一門課，只要標籤輪廓接近也算相似。
這是協同過濾和 User Embedding 的銜接點。

### 4.4 冷啟動

| 情況 | 退路 |
| --- | --- |
| 新使用者，沒有互動 | 有歷史修課就已經有向量（3.3）；完全沒有時退到同系同年級熱門選修，再退到不給 CF 分數 |
| 新課程，沒人選過 | CF 不給分（`null`），由興趣檔案與向量分數負責 |
| 整體使用者太少 | CF 整個停在 shadow |

### 4.5 隱私

1. **同意範圍：新增一種隱私同意（已決定）。** `personalization_learning` 的語意是
   「用我的資料改善我的推薦」；協同過濾會把資料用來推薦給別人，是不同的用途。

   | 項目 | 構想 |
   | --- | --- |
   | `purpose` 名稱 | `collaborative_learning` |
   | 隱私中心顯示文字 | 「讓我的修課與課程互動紀錄（不含學號與姓名），協助推薦課程給其他同學」 |
   | 預設 | 不同意（opt-in），與 `personalization_learning` 一樣是可選項 |
   | 前提 | 必須先同意 `personalization_learning`；撤回 `personalization_learning` 時一併視為撤回 |
   | 貢獻與接收分開 | **貢獻**（我的資料進共現表）需要新同意；**接收**（我看到 CF 分數）只需要 `personalization_learning`，因為計算我的分數只用到我自己的資料加上已彙總的共現表 |
   | 撤回 | 下一次每日重算起不含他的資料；共現表整張重建 |
   | 要改的地方 | `Privacy_Consents.purpose` 允許的值、隱私中心頁（`PrivacyPage.jsx`）、`privacyConsentAdapter.js`、本人匯出、隱私政策版本號、`DATA_SCHEMA.md` 與 `API_SPEC.md` |

   既有使用者不會因為功能上線而自動被納入；Persona 帳號的同意由 `personaConsentSeed.js`
   另外決定，`source` 照例標 `persona_seed`。

2. **最小人數。** 一組共現至少 k 人（4.6 訂為 3）才納入，避免「選了 A 也選 B」其實只是某一位同學。
3. **撤回。** 撤回後下一次重算不得包含他；彙總表整張重建。
4. **推薦理由不透露個人。** 只說「修過這門課的同學也常選」，不出現小到可回推的人數。

### 4.6 啟用門檻（已調低）

| 項目 | 第二版 | 第三版 |
| --- | --- | --- |
| 真實且同意 `collaborative_learning` 的使用者數 | ≥ 30 | **≥ 15** |
| 每人非必修互動（歷史修課可計入） | ≥ 5 | **≥ 3** |
| 單一共現的最少人數 | ≥ 5 | **≥ 3** |
| 離線切分 | 每人依時間切，最後一學期當測試，不得用到測試期間的互動 | 不變 |
| 比較對象 | 非個人化、興趣檔案、標籤向量、CF、全部合用 | 不變 |

調低門檻的代價與配套：

- **共現 3 人是隱私上的下限，不建議再低。** 低於 3 人時，「修過 A 的同學也修 B」
  很容易被同班同學對應到具體的人。
- **15 人的評估結果，統計上多半會是「無法判定」。** 這是預期中的；門檻的意思是
  「可以開始 `active` 試行」，不是「已證明有效」。報告必須如實寫出樣本數。
- **試行期間 `α_cf` 固定在 5.1 的起始值 0.1**，即使單門課 CF 分數是 ±1，
  也只影響基礎分的 ±10%，不會讓 CF 主導排序。
- **退場條件**：試行期間若 shadow 比較顯示加入 CF 後的指標比不加還差，回到 `shadow`。

歷史修課計入後，「每人 3 筆非必修互動」對大二以上學生多半一開始就滿足，
實際的瓶頸是**同意 `collaborative_learning` 的真實使用者人數**。

這些數字仍是起點，不是依資料算出來的。Persona 資料只能驗證管線與方向，
不能用來校準門檻或決定對真實使用者啟用。

## 5. 接進排課流程

### 5.1 分數：各自加到原始分數上

```text
候選分 = 基礎分
       + α_tag × 基礎分 × s_tag      ← 興趣檔案（現有，等於現在的 基礎分 × (1 + α_tag × s_tag)）
       + α_vec × 基礎分 × s_vec      ← 標籤向量相似度（新）
       + α_cf  × 基礎分 × s_cf       ← 協同過濾（新）
       + 學分分 + 文字偏好分 + 舊關鍵字分 + 集中分 + 難易分   ← 現有的獨立加項，不變
```

- **三項分開計算、分開加，不先混成一個分數。** 每一項都寫進推薦理由的分數明細，
  看得出是哪個模型加了多少。
- 某個模型沒有分數（`null`）就該項為 0，不影響其他項。
- 每一項都乘上基礎分，原因和現在的標籤興趣相同：興趣只在「本來就能選的課」之間調整順序，
  不會讓一門基礎分是 0 的課因為興趣分數高就被選進來。
**α 的上限（已訂）**

| α | 起始值 | 說明 |
| --- | --- | --- |
| `α_tag` | 0.6 | 現在的值，不變；現有行為完全不受影響 |
| `α_vec` | 0.2 | 和興趣檔案都來自 rag_tag，高度相關，給小一點避免同一個訊號算兩次 |
| `α_cf` | 0.1 | 證據最弱（樣本最少），給最小 |
| **總和上限** | **0.9** | 三個 α 加起來不得超過 0.9 |

- 每個 s 都在 −1～1，所以三項合計的調整範圍是基礎分的 **−90%～+90%**，
  也就是基礎分乘上 0.1～1.9。現在只有標籤興趣時是 0.4～1.6。
- **為什麼是 0.9**：現在 +60% 已經實測過（10/11 的 Persona 重播），不改；新增的兩項合計
  只再給 +30%，讓新模型有影響力但不會壓過已驗證的興趣檔案。上限 0.9 而不是 1.0，
  是為了讓扣分最多到 −90%，課程不會因為興趣分數被扣到 0。
- 之後依 shadow 結果調整個別 α 時，**總和上限 0.9 不變**；要調高總和需要另外決定。
- 某一項在 `shadow` 或 `off` 時，該項以 0 計入，其他項的 α 不會自動放大補上。
- 實作時加一個檢查：設定的 α 總和超過 0.9 時拒絕啟動，而不是靜默截斷。

方案層同樣分開：

```text
方案分 = 方案偏好分 × (1 + α_tag × 平均 s_tag + α_vec × 平均 s_vec + α_cf × 平均 s_cf)
```

每一項的平均只計入有分數的自由選擇課，涵蓋率分開記錄（沿用 `tagInterestCoverage` 的作法）。

### 5.2 資料流

```text
排課請求
  └─ scheduleService.js
       ├─ 讀興趣檔案 → tagInterestContext                    （現有）
       ├─ 讀使用者向量 ＋ 候選課的標籤向量 → vectorInterestContext （新）
       └─ 讀 item-item 鄰居表 → cfContext                    （新）
              三個 context 結構相同：coursesBySectionId[sectionId] = { score, evidence, reason }
  └─ scheduler.js
       ├─ 單課：照 5.1 分別加三項
       └─ 方案：照 5.1 分別乘三項
```

三個 context 分開傳進 `scheduler.js`，不在 `scheduleService.js` 先合併。
現有保護原樣適用於三項：

- 必修與使用者指定課程不套用任何一項。
- 只作用在非負的基礎分上。
- 衝堂、學分上限、避開時段由求解器與 `scheduleValidator.js` 把關，興趣分數碰不到。

`scheduler.js` 需要改的是：計分處從讀一個 context 改成讀三個，以及推薦理由明細多兩欄。
這比第一版（只讀一個混合分數）改動大，但換來每一項都可追蹤。

| --- | --- |

## 9. 已知風險

| 風險 | 說明 | 對策 |
| --- | --- | --- |
| 興趣檔案與標籤向量高度相關 | 兩者都來自 rag_tag，分開加會讓標籤訊號被算兩次 | shadow 階段量兩者的相關係數；`α_vec` 從小開始 |
| 歷史修課的偏誤 | 學生修某門課可能只是時段剛好或學分需要 | 歷史修課預設只給 +0.5；彈出視窗讓使用者修正 |
| 標籤品質 | 向量完全依賴 rag_tag；標籤錯了，相似度就錯 | 階段 1 人工抽查 |
| 熱門偏誤 | CF 會把熱門課推得更熱門 | 相似度已除以各自人數；另量 coverage |
| 回饋迴圈 | 推什麼就選什麼，模型再學到「他喜歡這個」 | 曝光事件已記錄 `displayedSet`；探索功能負責打破 |
| 人造資料誤導 | Persona 的行為是設定的 | 只驗證管線與方向，不校準門檻、不作啟用依據 |
| 標籤 embedding 把不同義的詞拉近 | 例如兩個領域都叫「模型」 | 送進 API 時附上分類路徑；τ 由人工抽查定；相近表只存前 5 名 |
| API 模型下架或改版 | 新舊向量不能混用 | 每筆記錄模型版本；換模型時全量重算；排課不即時依賴 API |
| 門檻調低後的誤判 | 15 人的結果多半無法判定，容易把雜訊當效果 | `α_cf` 固定 0.1；報告寫樣本數；設退場條件（4.6） |
