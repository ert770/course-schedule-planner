# 2026-08-31 Roadmap #26：每門推薦課的證據導向理由

## 1. 修改日期

2026-08-31

## 2. 為什麼做這件事

`#4`、`#5A`、`#21`、`#22` 都已完成，`#26` 的前置相依全部滿足。系統排得出課表，
但答不出「為什麼是這門課」。

三個具體斷點：

- **理由是方案的名字，不是課的理由。** 貪婪填充排入的課，`reason` 字串直接用
  `variant.title`——點開一門課想知道為什麼推薦它，看到的是「涼課與高分優先」。
- **Agent 根本看不到理由。** `agentService.js` 的 `compactCourse()` 沒有 `reason`
  欄位，模型從來不知道課為何被推薦，只能講空泛的話——而講空泛的話最容易變成編造。
- **前端也不顯示。** 只有「被排除的課」看得到原因，「被排進來的課」反而沒有。

另外 `#2` 的互動事件從 `#29` 建好起就預留 `recommendationReasonVersion`，
一直是 `null`，註記寫著「等 #26」。

## 3. 規劃時先量測，避免高估這件事的內容量

`#26` 列的 8 個欄位裡，「分數怎麼來的」與「誰輸給了它」聽起來最有價值，
但實測 demo 帳號（真實 MySQL）之後必須把預期講清楚：

**落選者現況是 0 個。** 16 門 eligible 全部不是排入就是被硬性排除（6 門已修過、
2 門衝堂），貪婪迴圈是**候選用完才停**（23/25 學分，沒撞到上限）。
把候選池放大到模擬 `#13C` 已解，落選者立刻變成 185 個。

| 情境 | 落選者 |
| --- | ---: |
| 現況（16 門可競爭） | **0** |
| 大池（模擬 #13C 已解） | **185** |

**分數組成算得出來，但 8 門排入的課裡有 5 門組成完全相同**
（`類別 -240 + 學分 36 + 內容偏好 80`）。對那 5 門，理由會是同一句話。

**結論：這兩項受制於 `#10` 剩下的同一個瓶頸（`#13C` 把候選池從 227 壓到 16）。**
機制照做，但驗收重心放在今天真正有內容的「證據」那半邊。

## 4. 主要改動內容

### 4.1 分數組成：一個公式，兩個出口

抽出 `computeScoreComponents()` 回傳各項分數，`scoreCourse()` 改成
「把這個物件加總」。**公式只有一份**，解釋用的數字與排序用的數字不可能漂移
（R7 釘住「組成總和 === 總分」，比照 `#23` 的 G10）。

同樣手法套用在偏好判定上：`collectContentPreferenceHits()`／`collectInterestHits()`
回傳命中明細，`getContentPreferenceScore()`／`getInterestScore()` 退化成加總的薄包裝
——命中了哪幾項原本算完就丟，現在是解釋的原料。

### 4.2 理由物件

新增 `server/src/skills/recommendationReason.js`（純函式）。**它只解釋既有決策，
不參與決策**——不重新判定任何規則，`isRequiredForStudent()`、
`resolveCourseEligibility()`、`deriveReviewEvidence()` 的結果一律沿用。

理由掛在 `addCourseToPlan()` 裡組裝，因為**放置當下才知道的事實**都在那個函式中
（時段偏好豁免、是否使用者指名、是否本人必修）。搬到外面組裝就得把這些再傳一次，
等於製造第二個真相來源。

`confidence` 由證據完整度決定，規則寫死不憑感覺：資格待確認或系所範圍無法解析
→ `low`（連能不能修都還沒確定）；涼度只是推估或完全沒有評價 → `medium`；其餘 `high`。

`dataSources` 只列**實際查過**的來源——沒有評價的課不得列 `Course_Reviews`，
否則「可追溯」就變成裝飾。

### 4.3 誰輸給了它：一個開發中抓到的假資料

貪婪迴圈記錄落選者的時間點是**做決定的當下**，那時還不知道排在後面的課稍後
會不會也被排入。第一版實作直接記錄 runner-up，實測發現
**18 筆記錄裡有 16 筆（89%）最後自己也進了課表**——把它們說成「輸給某某課」是假的。

修法是在 `finalizePlan()`（greedy 與 `#22` repair 的共同出口）加一道
`reconcileAlternatives()`：剔除最後也被排入的課，並替真正的落選者補上
`notScheduledBecause`（它最後為什麼不在課表）。修正後假資料 0 筆。

`alternativesRejected.status` 用三態表達，不用空陣列含糊帶過：

| status | 意義 |
| --- | --- |
| `had-competitors` | 有課真的輸給它 |
| `no-competitors` | **確實沒有競爭者**，不是還沒算 |
| `not-applicable` | 這條放置路徑不經過競爭（必修迴圈、關注課程） |

### 4.4 接到 Agent

`compactCourse()` 加上理由的精簡版。**刻意不送 `scoreBreakdown`／`scoreTotal`**
——分數是內部排序用的，對使用者講「這門課得了 956 分」沒有意義，
而且會把 input 撐大，那正是這個投影函式存在的原因。

`promptService.js` 的 system prompt 與 `docs/PROMPT_DESIGN.md` 同步加上使用限制：
只能轉述理由物件裡有的東西；`matchedPreferences` 為空就照實說沒命中；
`no-competitors` 不得說成「勝過其他所有課」；`dataSources` 沒列到的來源就是沒查過。

### 4.5 填上 `recommendationReasonVersion`

`scheduleService.js` 的 `buildExposureDraft()` 從 `null` 改為
`RECOMMENDATION_REASON_VERSION`。schema、DB 欄位與讀取路徑 `#2`／`#29` 都已備妥，
這裡是一行接線。

### 4.6 前端

`SchedulePage.jsx` 與 `DashboardPage.jsx` 原本各有一份幾乎相同的課程詳情彈窗，
而且**已經開始漂移**（Dashboard 少了地點與時間）。先抽成
`client/src/components/CourseCard/CourseDetailModal.jsx` 再加理由區塊——
推薦理由是一段有實質規則的 UI（什麼時候能講涼度、什麼時候要說沒有依據），
複製兩份必然走樣。

抽取過程中發現自己把 `⏰ 上課時間` 弄丟了，已補回（見第 6 節）。
