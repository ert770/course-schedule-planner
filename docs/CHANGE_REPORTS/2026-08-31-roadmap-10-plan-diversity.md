# 2026-08-31 Roadmap #10：修復多方案塌縮

## 1. 修改日期

2026-08-31

## 2. 為什麼做這件事

`#21`、`#22` 完成後 `#10` 的前置相依全部滿足。系統宣稱產生 5 種不同取向的課表方案，
實際上 demo 帳號只拿得到 **1** 份。

**開工前先重新量測，發現 roadmap 記載的根因已經過期。** 那份診斷寫於 2026-08-01，
用的是 55 門的假資料（`server/data/courses.json`）。改用**真實 MySQL 與 demo 帳號**
重測後，「15 門必修互相衝堂 11 對、低年級只剩 1 學分填充空間」在現在的系統上不存在：

- demo 帳號候選池只有 **3 門必修**，而且**三門都已經修過並通過**，
  最終課表一門必修都沒有；
- `#13A` 的系所收斂與 `#19` 的已修排除上線後，那個現象就消失了。

## 3. 真正的原因（全部經實測）

### 3.1 五個 variant 是「同一組基礎分 + 一點小加分」，而小加分太小

| 項目 | 改動前量級 |
| --- | --- |
| 類別（`getEffectiveCategoryPriority × 120`） | 跨級距 **120～480** |
| `INTEREST_KEYWORD_SCORE` | 40／命中 |
| `max_credits`（`credits × 25`） | 2↔3 學分只差 **25** |
| `easy_score` | 0～100，**無評價時為常數** |
| `compact` | ±120／重疊天 |

主題訊號被類別分完全蓋過，五個 variant 排出同一份課表，去重後只剩 1 份。

### 3.2 兩個 variant 根本沒有訊號可用

- **`easy_score`**：實際參與競爭的 10 門課裡只有 **1 門有評價**，涼度分數幾乎是常數，
  排序與 `required_first` 近乎相同。
- **`interest`**：0 門命中關鍵字。追下去發現原因不只是關鍵字寫得不好——
  `constraintService.js` 的 `prefs.interests ?? prefs.preferenceTags` 中
  `prefs.interests` **這個欄位並不存在**，因此永遠退回偏好標籤，把
  `#不排早八`、`#全英授課`、`#盡量集中排課` 這些**排課偏好**當成**興趣主題**
  拿去比對課名與課程介紹。兩者是不同的東西，當然永遠比不中。

### 3.3 候選池太小（不在本次可解範圍）

227 門候選裡 **211 門**因「適用對象規則尚未確認」被保守排除（208 門 B 類通識、
2 門 C 類學院綜合班、1 門 E 類學分學程），真正能競爭的只剩 16 門。這卡在 `#13C`
（等系辦／校方正式規則），寫程式解決不了。

實測兩個原因的相對影響：

| 情境 | 去重後方案數 |
| --- | ---: |
| 現況（16 門可競爭） | 1 |
| 把候選池放大到可競爭 195 門 | 3 |

**兩個原因都是真的**：池子太小會塌縮，但就算放大，仍有 variant 產不出不同的東西。

> **過程中我犯了一個量測錯誤，一併記錄。** 我最初量到「16 門可修課 0 門有評價」，
> 那是錯的——`reviewEvidence` 是在 `prepareCandidates()` 裡才掛上去的，
> 我讀的是還沒掛上的原始候選物件。正確數字是**實際競爭的 10 門課裡有 1 門有評價**。
> 另一個錯誤是我第一次「放大候選池」的實驗只改了 `eligibility` 欄位，
> 但該欄位在 `prepareCandidates()` 內會重算，實驗其實沒有生效（排除原因逐項相同），
> 因此一度誤判「池子大小不是原因」。改成調整班級名稱後才真正放大，結論才成立。

## 4. 主要改動內容

### 4.1 每個 variant 一張權重表

`scheduler.js` 新增 `VARIANT_WEIGHTS`，每個 variant 一組係數
（`category`／`credits`／`easy`／`interest`／`compact`）。係數是「相對於既有基準」
的倍率，因此 **`required_first` 全部維持 1／0，行為與改動前逐項相同**，
可作為對照組；其餘 variant 降低類別係數、拉高自己的主題係數。

`compact` 的係數刻意高於「使用者自己勾了集中排課」的基準（1）——實測 demo 帳號
本來就開著集中排課，係數設 2 時這個方案仍與其他方案相同。這個方案的語意是
「比你平常更集中」，不是「跟你平常一樣集中」。

### 4.2 必修的絕對優先抽出來（本次唯一有回歸風險的地方）

類別分變成可調之後，一門替代涼度很高的一般選修可能壓過必修。因此本人必修改由
`REQUIRED_COURSE_BONUS` 固定加分取得絕對優先，**不受權重表影響**，權重表只排序選修。

判定直接沿用 `getEffectiveCategoryPriority()` 的結果（priority 為 0 才給），
不另寫一份 `isRequiredForStudent()` 判斷——否則「非本人必修要降級」這條規則
會有兩個實作，遲早漂移。

### 4.3 涼度替代訊號與 `easinessSource`

無評價時改用替代訊號讓 `easy_score` 仍排得出不同課表，並在每門課標記來源：
`reviews`／`proxy`／`none`。

**只用實測有區分力的訊號**（對 16 門可修課量測關鍵字命中）：
討論／互動／參與 8/16（最有效）、實作／實驗／專題 13/16、學分數。
**排除**期中考 0/16、期末報告 0/16、深入進階應用 16/16——這三組完全無法區分，
加進來只是雜訊。關鍵字重用 `CONTENT_PREFERENCE_RULES` 既有定義，不另造詞表。

**誠實邊界沒有放寬**：`proxy` 只影響排序，**不進** `plan.reviewCoverage`，
也不讓方案層 `preferenceBreakdown.easy` 冒出數字——那兩者只認真實評價
（`#4` 的 ADR-006／ADR-008）。`PROMPT_DESIGN.md` 明訂 `proxy` 只能說
「依課程屬性推估」，不得說涼／好拿分。P10-5 釘住這條界線。

### 4.4 移除 `interests` 的偏好標籤回填

`constraintService.js` 改為 `pickList(input.interests, prefs.interests)`。

**先講清楚效果**：實測把 `interests` 換成真的主題關鍵字後方案數仍是 3，
**這個修正本身不會增加方案數**。做它的理由是這個欄位餵的是錯的東西，
讓「興趣」這個維度從來沒有被真正測過。

### 4.5 方案數不足時說明原因

`warnings` 新增一句：哪些取向被合併、可競爭的課程數。使用者若已勾集中排課，
另外說明該方案為何不會不同——那是合理結果，不是缺陷。

## 5. 影響範圍

- `POST /api/schedule/generate`、`/api/chat` 的 `run_csp_scheduler`：
  課程新增 `easinessSource` 欄位，`warnings` 可能多一句說明。**既有欄位語意不變。**
- **主推方案（`plans[0]`）可能改變**——這是使用者實際看到的課表。實機驗證見第 6 節。
- 排課引擎的硬限制、validator、隱私與互動記錄路徑都沒有改動。

## 6. 測試與驗證結果

### 自動化

- `npm test`：**786 pass / 0 fail**（改動前 770，新增 16 項 P10 案例），golden set 8/8。
- 既有 S1-S17、N1-N15、X1-X16、Z1-Z7 全數通過，零回歸。
- `node --check`、client `npm run build`／`npm run lint` 皆通過。

### 量測 A/B（真實 MySQL、demo 帳號）

| 情境 | 改動前 | 改動後 |
| --- | ---: | ---: |
| 小池（16 門可競爭） | **1** 個方案 | **2** 個方案 |
| 大池（模擬 #13C 已解） | 3 個方案 | 3 個方案，但 `easy_score` 的課表真的不同了 |
| 大池 + 真興趣關鍵字 | 3 個方案 | **4** 個方案（`interest` 開始生效） |
| 大池 + 關閉 preferCompact | — | **4** 個方案（`compact` 開始生效） |

`compact` 在 demo 帳號上仍與其他方案相同，原因已查明且合理：**使用者本來就勾了
「盡量集中排課」**，每個方案本來就會集中。關閉該偏好後 `compact` 立即出現。

### 瀏覽器實機（demo 帳號 `D1249697`）

`/schedule` 按「自動排課」：

- 主課表**沒有回歸**：仍是 8 門課、23 學分，與改動前逐項相同。
- 畫面訊息由「已產生 **1** 個課表方案」變成「已產生 **2** 個課表方案，
  預設採用「必修與重補修優先」（偏好符合度 33%）：8 門課，共 23 學分。」
- 合併說明確實顯示給使用者：「集中排課、興趣與路徑優先、學分最大化排出的課表與
  其他方案相同，已合併，目前提供 2 種方案。可競爭的課程僅 16 門……（你已設定
  「盡量集中排課」，因此每個方案本來就會集中……）」
- API 回應確認 `easinessSource` 落地：8 門課中 7 門 `proxy`、1 門 `reviews`
  （`資訊安全管理`）。
- `read_console_messages` 無新增錯誤（只有重新登入前的既有 401）。

### 過程中修掉的一個測試錯誤

P10-1 原本斷言「必修排在選修之前」用的是 `plan.schedule` 的**陣列位置**。
實測（含改動前對照）該陣列本來就不是依優先度排列，必修可能出現在選修之後——
那是從來不成立的實作細節。已改為斷言「學分只夠一門時，五個 variant 都選必修」，
測的是「必修優先」這條真正的規則。

## 7. 明確不做

- **不解決候選池太小**：卡 `#13C`（等系辦／校方正式適用對象規則）。
- **不做多方案比較 UI**：那是 `#27`。前端目前只顯示 `plans[0]`
  （`client/src` 僅 `interactionLog.js` 讀 `plans`），因此本次的可見範圍是
  主課表、方案數訊息與 warnings。
- **不改成連續權重向量**：那是 `#7`；本次是過渡修復，但權重表的形狀讓 `#7` 好接手。
- **不放寬「沒有評價就不得宣稱涼／好拿分」**。
